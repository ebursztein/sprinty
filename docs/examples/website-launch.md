# Launch a product website

Start with an idea for a product or service. Finish with website files, reviewed content, and a launch checklist. Research, design, writing, implementation, and review share one plan.

## Paste into your agent

```text
Use Sprinty to turn my website idea into organized work and build a reviewed first version.

Product or service: [describe it]
Audience: [who it is for]
Main action visitors should take: [what they should do]
Existing project or preferred stack: [describe it, or inspect the repository]

Read the project's instructions and Sprinty skills. Call info with the canonical repository path first; resume suitable existing work instead of duplicating it. Keep sprint state in a gitignored local data directory. If the server is unavailable, help me complete setup before claiming to use it.

Organize the work into feature-sized subsprints: research and direction; design and content; build and launch review. Create focused tasks with deliverables, dependencies, and appropriate checks before editing. Use real server-minted IDs. Share the dashboard URL.

Create an audience brief, page structure, visual direction, homepage content, and responsive website. Use the existing project conventions. Claim each task before working, keep decisions and progress with the task, and link artifacts to the work they support.

Verify the result with the project's build and tests, and review mobile layout, keyboard use, links, and copy. Distinguish executable checks from human/design review; do not invent passing results. Record a real commit and the evidence for completed tasks. Leave the website ready for a publication decision; do not purchase a domain or deploy it as part of this request.

After compaction or a new session, recover the current plan through info and sprint_resume, then inspect next and my claims before continuing. Finish with the deliverables, what was verified, and what remains on the launch checklist.
```

## What to look for

- The plan separates research, design, content, building, and review into tasks with clear deliverables.
- A design/copy review waits for both source tasks; publication waits for review.
- The dashboard's selected subsprint shows its tasks, owners, and dependencies.
- Completed work has resolving commits and recorded checks; pending review stays visible.

For a second-session check, start another session and ask it to resume the same repository and data directory. It should recover the plan rather than ask you to describe the project again. A restarted caller may need an explicit handover if its previous identity cannot be recovered; consult the installed tool skill.
